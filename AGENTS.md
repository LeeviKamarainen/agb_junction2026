# Junction 2026

FastAPI backend (`backend/`: uv, SQLModel on SQLite) and Next.js frontend (`frontend/`), run with Docker Compose (`compose.yaml`) on one Hetzner VM behind Caddy (`deploy/Caddyfile`). All backend routes live under `/api`. The visual memory for the glasses (`memory/`) runs on the Gemma server; see "Memory API" below.

## Commands

- `make dev`: backend on :8000 and frontend on :3000, both auto-reloading. Open http://localhost:3000; API docs at http://localhost:3000/api/docs.
- `make check`: the same checks CI runs (ruff, pytest, ESLint, typecheck, and the frontend's `*.test.ts` files with `node --test`).
- `make api-types`: regenerate `frontend/src/lib/api/schema.d.ts` after changing backend models or routes, and commit the result.
- `make up`: the production stack in Docker at http://localhost.
- `make reset-db`: delete the local database.

## Git workflow

`main` is production: whatever lands on it deploys. Every change goes through a branch and a pull request.

1. Branch from an up-to-date `main`: `git switch main && git pull && git switch -c <short-topic>`.
2. Commit one concern at a time, with an imperative subject line that says what changed and a body that says why when it isn't obvious.
3. Before pushing, `make check` passes, `make api-types` has been rerun if backend models or routes changed, and the `review` skill reports nothing outstanding.
4. Push the branch and open a pull request with `gh pr create`, saying what changed, why, and how it was tested. CI runs the checks on it.
5. Merge with `gh pr merge <number> --squash --delete-branch` once the checks are green and a person on the team has explicitly approved it.

Anything that changes production needs that same explicit approval from a person: merging, pushing to `main`, `gh workflow run`, `make prod-reset-db` and `make prod-import-keys`. Keep published history intact: bring a branch up to date with `git merge origin/main`, undo published commits with `git revert`, and force-push only your own unmerged branch, with `--force-with-lease`.

## Database

There are no migrations, and a new database starts empty. When the models or the vector tables change, the next start carries the rows over, in production too (`init_db` in `backend/app/db.py`): it builds a database from the current models beside the old one and copies every table and column both have, ids included; a new column gets its default, or NULL when it is optional, and what the models no longer have is dropped. The old file stays beside it as `app.db.<time>.<old fingerprint>.bak` (the newest 5). What cannot be carried over stops the start with a message that says what to do, and leaves the old file as it was: in a table with rows, a new NOT NULL column without a fixed default, a column whose type changed, a vector table whose width changed (a new embedding model), or rows that break the new constraints. The backend then stays down until a fix or a revert of that model change is deployed. So give a new column a default or `| None`, and rename a column rather than change its type. Nothing else may open the database while the backend starts (no one-off commands on `/data/app.db` during a deploy): SQLite finds the WAL by the file's name, so a connection held across the swap would corrupt the new file. `make prod-reset-db` still wipes production on purpose, and what it deletes has no backup. The demo dataset is the admin's published demo clips (`/admin`), which `backend/app/demo.py` stores as demo memories (collection `demo`, owner 0) with the embedding model: a video as its frames at 2 fps like the glasses stream (near-duplicates skipped), an image sequence one memory per image, faces blurred first. It runs in the background after each start and whenever the admin changes a clip, and replaces the memories of a clip whose media changed or removes those of one unpublished or deleted (each memory's `source` names its clip). The clips survive a schema change like every other row, and after a deliberate wipe `showcase.restore` brings them back from the manifest `backend/app/showcase.py` keeps beside the database. Reasoning: `docs/adr/0003-carry-rows-over.md`.

Demos recorded with the glasses (stills under a tag) are kept in the repository instead: `make demo-pull TAG=<tag> API=https://<host>` downloads one into `backend/demo-data/<tag>/`, you commit it, and every start adds it as demo memories (`backend/app/demo_bundles.py`, `backend/demo-data/README.md`), so even a wiped database gets it back.

Database access is async (`backend/app/db.py`: SQLAlchemy on aiosqlite, `AsyncSession` from SQLModel): routes are `async def`, take `SessionDep` and await every query (`await session.exec(...)`, `await session.get(...)`, `await session.commit()`); outside a request, open one with `async with new_session() as session:`. Sessions keep their objects after commit, since an async session cannot reload an attribute lazily. The model clients (`backend/app/llm.py`) are async httpx too, so never call blocking I/O from a route; run CPU or file work such as image resizing or password hashing with `anyio.to_thread.run_sync`. SQLite still takes one writer at a time (WAL, `busy_timeout` 5 s). Tests stay synchronous: `TestClient` for routes, and the `db` fixture (`backend/tests/conftest.py`) to run `await work(session)` on the app's event loop; model fakes are `async def`.

Vector search lives in the same file, through the sqlite-vec extension (`backend/app/vectors.py`): declare a table in `VECTOR_TABLES`, then `await vectors.upsert(...)` and `await vectors.nearest(...)` with `await session.connection()` or a connection from `get_engine()`. Every row has a `created_at` timestamp (timezone-aware, defaults to now) that `nearest` can filter with `since` and `until`; extra metadata columns are declared per table and filtered with `where`. The vector tables count toward the fingerprint, so changing one carries their rows over like any schema change, except a changed width, which stops the start: vectors of another embedding model cannot be compared with the stored ones. The `memory/` API does not use it (see `memory/docs/decisions.md`).

## Accounts

One admin, who logs in with a password, sees every memory. Everyone else starts a temporary guest on `/guest` or the login page (`POST /api/auth/guest`): a generated name, no password, 60 minutes (`GUEST_MINUTES`), seeing the demo memories and the ones it added. An unexpired guest can return by username with `POST /api/auth/guest/login`, keeping its original expiry. The login page (`/login`) only shows guest options; the admin logs in with a password on the unlinked `/admin`. An expired guest is deleted with its logins, memories and their image files, and goals with their triggers (`purge_expired_guests`: at startup, every 5 minutes, and whenever a guest starts or an expired login is used). Code: `backend/app/auth.py`, routes in `backend/app/routes/auth.py`. The admin is created, or its password reset, on every start from `ADMIN_USERNAME` (default `admin`) and `ADMIN_PASSWORD`; without a password a random one is printed in the backend log. In production set it with `gh secret set APP_ADMIN_PASSWORD`. A login is a token in an HttpOnly `session` cookie, or `Authorization: Bearer <token>` for the phone app (`/login` and `/guest` return it).

Every memory has an `owner_id` (0 = demo, which only the admin adds, with `demo=true`), copied into `memory_embedding` as `owner`. Anything that reads memories takes the viewer's scope (`Viewer.owners`, `None` for the admin): listing, images, `vector_search` and its keyword search, and `agent.run`, so the chat model only ever receives the asker's memories and stills. Goals and triggers are per user. `frontend/src/proxy.ts` only redirects pages to `/login` without a cookie; the backend decides access. A model change keeps everyone logged in, since the logins are carried over with the rest. Tests log in through the `client` (admin) and `guest` fixtures in `backend/tests/conftest.py`.

## Frontend

Read `frontend/AGENTS.md` before writing frontend code. The home page (`frontend/src/app/page.tsx`, its parts in `frontend/src/app/_home/`) plays one published demo clip at a time through the glasses view (`frontend/src/components/glasses-view/glasses-view.tsx`: the whole picture, never cropped, on a blurred fill, a glasses frame drawn over it, and the glasses' 600×600 display (`glasses/display.tsx`) in the right lens), with the clip's scripted prompts and trigger messages on the display (`glasses-view/cue-screens.ts`), a clip picker, sound, and **Try it out**, which opens `/try` with that clip. `/try` (`frontend/src/app/try/`) is the same view, live, on a demo clip or the visitor's camera (front or back on a phone). One memory is in play at a time, cut at now: the clip's frames from its start to the playhead, or the visitor's own camera frames (collection `glasses`). Questions (typed or hold-to-talk: `/api/ask` with `demo_clip_id` and `demo_at_s`, or `collections: ["glasses"]` on the camera), déjà vu (`/api/glasses/command`, with the clip and second too) and the map all see only that memory. **Start** begins a guest session when nobody is logged in (`ensureSession` in `lib/session.ts`) and streams frames at 2 fps to `POST /api/glasses/frames` against the visitor's goals, as the glasses do (clip frames with `store=false`, since the clip's frames are demo memories already; camera frames are stored). Pause stops time: nothing new is remembered or fires. There is no seeking; Replay starts the clip's memory over. An answer shows in the right lens as the backend's `memory_answer` screen, a trigger's message as the Android app draws it (`glasses-view/screens.ts`, which copies both, so change them together), with the frame the answer rests on (the answer step's `evidence`: the memories Gemma cited); answers and messages are spoken when sound is on, and the goals are chips under the view. Beside it, the memory map (`try/memory-trail.tsx`) has one point per remembered frame, projected in the browser (`memory/pca.ts`) and revealed as the playhead passes it (`GET /api/memories/vectors?clip=<id>`, whose `clip_at_s` is each frame's second in the clip; camera frames are fetched with `after_id` as they are stored); a point shows its frame on hover, and the evidence is ringed. `/admin` manages drafts, uploads, ordering, publication and each clip's scripted prompts; published media is public, drafts require the admin, and publishing makes a clip searchable. Visitors never log in and see the home page and Try it; the admin logs in on `/admin` and also gets demo management, the stream wall (`/admin/streams`), the Memory lab (`/memory`, which `components/admin-only.tsx` keeps for the admin) and the glasses harness (`/glasses`: only the link is the admin's, anyone logged in can open it). Logging out goes to the home page (`UserMenu`), and tells every `useSession` at once (`loggedOut()` in `lib/session.ts`). Every page shares one header (`frontend/src/components/site-header.tsx`, also inside `components/site-shell.tsx`), and the glasses harness and Memory lab use it too. The theme is a Nordic dark palette in `globals.css`; the harness (`glasses/glasses.css`) takes its colours from those tokens, except the simulated display. The stream wall shows every client sending frames right now, grouped by app, each with its newest frame about twice a second and a log of what its user sent: questions and goals, and the triggers that fired. Clicking a tile opens the stream in full (`/admin/streams/<id>`): its frames large, with fullscreen, and a verbose backend log like the Memory lab's, with what became of every frame (stored or why not, each trigger's score against its level, what fired), Gemma's searches and answers (logged in `agent.run`), and errors, each with its JSON. Beside the frames is a chat (`stream-chat.tsx`): the admin asks Gemma about the stream as its user (`POST /api/admin/streams/{id}/ask/stream`, the same agent as `/api/ask/stream` over that user's and the demo's memories, with the newest frame attached), and Gemma's `start_watching`/`stop_watching` change that user's goals and triggers; the goals are listed above the chat and can be removed there (`GET`/`DELETE /api/admin/streams/{id}/goals`). A stream's owner is remembered after it goes quiet, so its page can still be asked about. The backend keeps only the newest blurred frame per feed, its last 400 frame results and the last 300 events per user, in memory (`backend/app/glasses/feeds.py`, routes `GET /api/admin/streams`, `/api/admin/streams/{id}` and `/{id}/frame`, admin only). Clients name themselves with a `client` field on `/frames` and the socket's `memory_frame` header (`live`, `harness`; a socket that does not is `glasses`, the Android app).

## Deploying

Each change that lands on `main` runs the checks, then deploys: the code is copied to the VM, `docker compose up --build` runs there, and the job waits for `https://<vm-ip-with-dashes>.sslip.io/api/health`. Follow it with `gh run watch`. A failed build keeps the previous version running. Roll back by merging a pull request that `git revert`s the bad commit, with one exception: never revert the carry-over in `init_db` (`backend/app/db.py`, ADR 0003) once it has run in production, since the code before it wipes a database whose fingerprint it does not know; put the first backup in place first. `gh workflow run ci-cd.yml --ref <branch>` deploys another branch until the next change lands on `main`.

## Production

- `make prod-logs`; `make prod-ssh` (the app is in `/opt/junction2026`, run `docker compose` there).
- `make prod-reset-db`: wipe production data on purpose, for good: only a schema change that was carried over leaves a backup, so copy `/data/app.db` first if it may be needed. The backend starts again with an empty database.
- `make prod-import-keys`: give everyone in `TEAM_GITHUB_USERS` (Makefile) SSH access with the keys on their GitHub accounts.
- Secrets: `gh secret set APP_<NAME>` (only the repo owner can) becomes `<NAME>` in the backend's environment on the next deploy; `gh variable set APP_<NAME>` for non-secret settings. Locally, put `<NAME>=...` in `backend/.env`.

## Memory API

`memory/` is the visual memory for the glasses: frames are posted to its API, have their faces blurred (`memory/src/glass_memory/faces.py`, the same file as the backend's), are embedded with EmbeddingGemma 2 and stored as memories, shown as a 2D map, and Gemma answers questions from the stills a question retrieves. Read `memory/README.md` before working there; what is left is in `memory/docs/todo.md` and the choices already made in `memory/docs/decisions.md`. It is its own uv project (Python 3.14 with torch, about 6 GB), so `make check` and CI leave it out: run `make check-memory`.

The API runs on the Gemma server (called VM2 in `memory/`), beside vLLM, behind Caddy at `https://<vm2-ip-with-dashes>.sslip.io`. Nothing deploys there automatically, so `make memory-deploy` and `make memory-setup` need the same approval as other production changes. Leave the `gemma` container and port 8000 alone.

- `make memory-deploy`: copy `memory/` to `/opt/glass-memory`, install it and restart the `glass-memory` systemd service. `make memory-setup`: once on a fresh server, after the first deploy.
- `make memory-logs`; `make memory-ssh`.
- `make memory-link`: the map page's address with the token in it, to share.
- `make memory-token`: the token API clients need (works for whoever `make memory-ssh` works for).
- `make memory-send FRAMES=<folder>`: post a folder of JPEG stills as one batch, the folder given from the repo root (needs `uv sync` in `memory/` first).
- The server's address is `VM2_IP` in `memory/.env`, which is not in git. Its secrets live only in `/opt/glass-memory/.env`: `GLASS_API_TOKEN` and `GEMMA_API_KEY`.

Calling it: every route except `GET /` and `GET /health` needs `Authorization: Bearer <GLASS_API_TOKEN>`, else 401. That is the only token this API takes: `GEMMA_API_KEY` is vLLM's (port 8000) and `SEGMENTER_API_TOKEN` is the segmenter's, and neither works here. Never commit the token; read it from the environment. Every route and its answer is in `memory/src/glass_memory/README.md` (HTTP API); the common ones:

```bash
URL=https://<vm2-ip-with-dashes>.sslip.io
AUTH="Authorization: Bearer $GLASS_API_TOKEN"
curl -H "$AUTH" -F frames=@0001.jpg -F frames=@0002.jpg -F every_s=1 $URL/batches   # {"batch", "memories", "summary"}
curl -H "$AUTH" $URL/batches                                                          # newest first
curl -H "$AUTH" -H "Content-Type: application/json" -d '{"question": "where are my keys?"}' $URL/batches/<batch>/ask
curl -H "$AUTH" -H "Content-Type: application/json" -d '{"model": "google/embeddinggemma-2", "input": ["keys"]}' $URL/v1/embeddings
```

`/v1/chat/completions` passes OpenAI-style chat, tool calls included, to vLLM on the same server (`GEMMA_URL`, `GEMMA_API_KEY`), so the backend reaches Gemma with this API's token: `LLM_URL` is the memory API's address and `LLM_API_KEY` its `GLASS_API_TOKEN`. It needs a `make memory-deploy` to go live.

`/v1/embeddings` serves EmbeddingGemma 2 (`google/embeddinggemma-2`), 768 numbers per input, in the same space as the stored stills; an input that starts with `data:image/` (a base64 data URL) is embedded as an image, its faces blurred first, any other as text: as a search query, or with `"input_type": "document"` as a text to be found (the backend embeds its notes that way). It replaced CLIP (`ViT-B-32`, 512 numbers) on 2026-11-14: that name now gets a 400, and vectors made with it cannot be compared with new ones.

## Glasses

`/glasses` in the frontend is a harness standing in for the glasses (webcam, mic, speakers, a 600×600 display); `glasses-android` is the real client. Both call `/api/glasses/*` (`backend/app/routes/glasses.py`) and draw the `GlassesReply` they get: the screens live in `backend/app/glasses/screens.py`, built only from the SDK's display components in `layout.py`, so a screen that works in the harness can be sent to the glasses. What the wearer says arrives as text in a `question` and goes to the memory as it is: nothing matches it to commands first, and Gemma answers through `agent.answer`, as `/api/ask` does (it needs the chat and embedding models, `LLM_URL` and `EMBED_URL`). Tests replace `optional_chat` and `optional_embedder` through `app.dependency_overrides`.

The display has no buttons and stays empty while idle; a reply that shows something sets `dismiss_after_s`, after which the client clears it. The wearer acts through the Neural Band's double index-finger tap (action `double_tap`, the same as `ask`), which replies with `client_action: "listen_question"`: the client opens its mic, shows only a blinking red light in a corner, and sends the words back as `{"question": ...}`. A question that starts "remind me…" or "warn me…" (or "tell/alert/notify me…") sets up a goal instead: the chat model writes its triggers (`triggers.write`, `glasses/triggers.py`), exactly as asking for it in the chat does, and they watch that user's memory stream from then on (`glasses/frames.py`); there is no other kind of warning. One like "where do I know this from?" is déjà vu (`glasses/dejavu.py`): the wearer's newest still, at most 30 seconds old, is looked up among their earlier stills, and the chat model says strictly which of the three closest show the same thing. On /try's demo clips the command also carries `demo_clip_id` and `demo_at_s`: the clips are demo memories, so the clip's frame at that point is what is in view, and "before" is only that clip's earlier frames outside the current look. Without them (the camera, the glasses), "before" is the asker's own stills, not the demo memories.

The live traffic runs over one WebSocket per client, `/api/glasses/ws` (`backend/app/glasses/channel.py`, which documents the protocol): JSON text messages with a `type`, and a frame as a small JSON header followed by the JPEG as a binary message. The client sends `command` (as `POST /command`), `memory_frame` (as `POST /frames`; one in flight at a time, a trigger that fires comes back in its `memory_result`) and `ping`; the server answers `reply`, `memory_result`, `error` and `pong`. Each message runs as a coroutine with its own session, at most 4 at a time per client, and the socket and the HTTP routes share `glasses/actions.py`, so `/command` and `/frames` keep working (the harness uses HTTP for the home screen and its memory stream). The socket needs a login like the HTTP routes (see Accounts): the browser's `session` cookie, `Authorization: Bearer <token>`, or a first `{"type": "auth", "token": ...}` message with the token `/api/auth/login` returned (never a query parameter: uvicorn logs URLs), else it closes with 1008. Everything it does is scoped to that user. The harness connects to the same origin: Caddy passes the upgrade in production, and `next dev`'s `/api` rewrite proxies it locally. Tests use `TestClient.websocket_connect`; its frontend types are hand-written in `frontend/src/app/glasses/channel.ts`, since a WebSocket is not in the OpenAPI schema.

A frame upload (`memory_frame` over the socket, or `POST /api/glasses/frames`) can carry a `collection` tag, which is the collection its memory is stored under (`glasses` when blank): the Android app uses it to record tagged demos.

Every image the backend receives has its faces blurred by `faces.anonymise` (`backend/app/faces.py`) before anything stores, embeds or describes it: in `glasses/actions.py` (`memory_frame`, for the HTTP route and the WebSocket alike) and in `POST /api/memories/image`. Images stored before this was added keep their faces. A new way in for images must do the same: `backend/tests/test_faces.py` fails for a new multipart upload route until it is listed and tested there, but it cannot see a new WebSocket message or a base64 image in JSON, so give those a test there yourself. Why a fill, and how many faces it finds: `docs/adr/0002-anonymise-faces.md`.

## Agent skills

Skills live in `.agents/skills/` (`.claude/skills` is a symlink to it; edit the real path): `add-feature`, `ship`, `review`, `submission`.

The database starts empty: there is no built-in sample-day loader. The Memory tab and `/glasses` share `GlassesHarness`; streaming posts frames through `/api/glasses/frames` and microphone questions use the glasses WebSocket. Manage goals and triggers in the Memory tab.
