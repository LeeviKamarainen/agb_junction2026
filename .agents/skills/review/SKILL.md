# Review

A change reaches production when its pull request merges, so this review is the last check before a person approves it. If your tool can start a subagent, run these steps in a fresh one and pass it only the diff, so the review is not anchored on how the change was written.

1. Collect the change: `git diff origin/main...HEAD` plus uncommitted work (`git diff HEAD`), or `gh pr diff <number>` for a pull request you were asked to review.
2. Check every changed file against every rule:
   - **Scope**: the change does one thing; unrelated edits belong in their own pull request.
   - **Secrets**: keys, tokens and passwords stay out of git; production values come from `APP_*` GitHub secrets, local ones from `backend/.env`.
   - **API types**: a change to backend models or routes ships with `frontend/src/lib/api/schema.d.ts` regenerated by `make api-types`.
   - **Data**: demo data the change relies on is in `backend/app/seed.py`, since production data is wiped whenever models or seed data change.
   - **Conventions**: backend routes are registered under `/api` from `backend/app/routes/`; server code calls `@/lib/api/server`, client code `@/lib/api/browser`.
   - **Leftovers**: debug output, commented-out code, unused files, and the example Note feature once a real feature exists.
   - **Demo-breaking bugs**: empty states, error paths, wrong status codes, anything a live demo would hit.
3. Run `make check`.

Done when every changed file has been checked against every rule and `make check` has run. Report each finding as `file:line`, the problem and the fix, or state "no findings".
